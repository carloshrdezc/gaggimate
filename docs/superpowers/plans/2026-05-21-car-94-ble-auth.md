# CAR-94 BLE Authentication & Encryption Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Lock the controller's BLE write surface (control characteristics + OTA RX) behind link-layer bonding and encryption so the unauthenticated `0xEF` flash-format command and every other write require a paired peer.

**Architecture:** Both ESP32s call `NimBLEDevice::setSecurityAuth(BOND, !MITM, SC)` + `setSecurityIOCap(NO_INPUT_OUTPUT)` during init. Every WRITE characteristic on the server flips to `WRITE_ENC` (OTA RX gets `WRITE_ENC | WRITE_NR_ENC`). Just-Works pairing on first boot persists an LTK in NVS; reconnects auto-encrypt. A pure helper `shouldWipeBondsBeforePair()` is extracted for host unit testing. Display surfaces a sticky `bleAuthFailed` flag over WebSocket so the web UI can guide a coordinated re-pair.

**Tech Stack:** C++17, Arduino-ESP32, NimBLE-Arduino 1.4.0, PlatformIO (envs `display`, `display-headless-8m`, `display-headless-4m`, `controller`, new `native` for host tests), Unity test framework, Preact web UI.

**Spec:** `docs/superpowers/specs/2026-05-21-car-94-ble-auth-design.md`
**Linear:** CAR-94 — every commit message ends with `(CAR-94)`.
**PR target:** fork `carloshrdezc/gaggimate` (not upstream).

```cpp
#ifndef GAGGIMATE_BOND_POLICY_H
#define GAGGIMATE_BOND_POLICY_H

#include <cstddef>
#include <cstdint>
#include <cstring>

// Host-buildable mirror of NimBLE's ble_addr_t layout. On-target we typedef
// from NimBLE's struct so the same call sites compile in both worlds.
struct gm_ble_addr_t {
    uint8_t type;
    uint8_t val[6];
};

#ifdef ARDUINO
#include <host/ble_hs.h>
using gm_ble_addr_t = ble_addr_t;
#endif

static constexpr size_t BOND_POLICY_MAX_BONDS = 3;

// Returns true if the local bond store should be wiped before attempting
// pairing. Logic:
//   - numBonds == 0                              -> false (nothing to wipe)
//   - numBonds >= BOND_POLICY_MAX_BONDS          -> true  (exhausted)
//   - stored peer null but numBonds > 0          -> true  (inconsistent state)
//   - stored peer != connecting peer             -> true  (peer factory-reset)
//   - otherwise (matching bond, normal reconnect)-> false
inline bool shouldWipeBondsBeforePair(size_t numBonds,
                                      const gm_ble_addr_t *storedPeerAddr,
                                      const gm_ble_addr_t *connectingPeerAddr) {
    if (numBonds == 0) {
        return false;
    }
    if (numBonds >= BOND_POLICY_MAX_BONDS) {
        return true;
    }
    if (storedPeerAddr == nullptr || connectingPeerAddr == nullptr) {
        return true;
    }
    if (storedPeerAddr->type != connectingPeerAddr->type) {
        return true;
    }
    return std::memcmp(storedPeerAddr->val, connectingPeerAddr->val, sizeof(storedPeerAddr->val)) != 0;
}

#endif // GAGGIMATE_BOND_POLICY_H
```

Create `docs/ble-pairing.md`:

```markdown
# BLE Pairing & Recovery

The display and controller communicate over an authenticated, encrypted BLE
link. They pair automatically on first boot and reconnect transparently
across reboots. You should never see a pairing prompt during normal use.

## First boot

Power on both devices. The display will connect to the controller and
complete pairing within ~5 seconds. After this, brew, steam, grind, and
OTA updates work normally.

## Recovering from a failed link

If the web UI shows **"BLE pairing failed — factory reset required"**, the
two devices' bonds have drifted (typically because one was reflashed or
factory-reset alone). Recovery is a coordinated re-pair:

1. Connect a serial console to **the controller** (115200 baud) and send
   the character `B`. The controller will log
   `Factory-resetting BLE bonds`.
2. Connect a serial console to **the display** and send `B`. The display
   will log the same.
3. Power-cycle both devices.
4. They will pair fresh on next boot, and the warning will clear.

## What this protects against

- An attacker in BLE range cannot send the OTA `0xEF` flash-format
  command, drive the boiler, valve, or pump, change PID settings, or
  trigger autotune — every write requires an authenticated, encrypted
  link.
- The one-time pairing window on first boot is the only opportunity for
  a man-in-the-middle attack. Pair in a trusted environment.

## Limits

- Bonds live in NVS. A full firmware re-flash that wipes NVS will require
  a coordinated re-pair (steps above).
- The controller has no UI for passkey display, so Just-Works pairing is
  used. MITM-resistant pairing (Passkey/Numeric Comparison) is not
  available on this hardware.
```
